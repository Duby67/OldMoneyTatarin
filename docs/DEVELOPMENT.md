# Подготовка окружения и сборка

## База проекта

Remote `origin` указывает на `https://github.com/Duby67/OldMoneyTatarin.git`, remote `upstream` — на `https://github.com/ElyPrismLauncher/Launcher.git`.

На 14 ноября 2026 года выбран последний стабильный PineconeMC `11.1.2`, commit `ac99ad44ef98dd73dd9626c7b7b2b668dd8cbd5c`. Чистая ветка `vendor/pineconemc` содержит полное дерево этого релиза и его историю, без наших документов и изменений. В отличие от ранее импортированной `develop` upstream, стабильная база содержит исправление проверки пути при импорте CurseForge-модпаков. В [релизе Prism 11.1.1](https://github.com/PrismLauncher/PrismLauncher/releases/tag/11.1.1) оно описано как исправление безопасности.

Субмодуль `libraries/libnbtplusplus` получен на commit `3538933614059f0f44388a2b16f3db25ce42285b`. После смены базы выполняется `git submodule update --init --recursive`.

Наш `develop` ранее содержал импорт дерева upstream без родительской связи. Для перехода на стабильную базу подготовлено слияние с двумя родителями: сохранена история нашего проекта и добавлена история `vendor/pineconemc`, рабочее дерево исходников заменено стабильным, наши документы сохранены. Слияние остановлено до коммита по правилам репозитория. После просмотра владелец должен завершить его коммитом; до этого не начинайте новые слияния и не переключайте ветки. Push не выполнялся.

Отдельная копия исходного README в нашей документации больше не требуется: оригинал доступен через `git show vendor/pineconemc:README.md`.

## Ветки и обновление upstream

| Ветка | Назначение |
| --- | --- |
| `vendor/pineconemc` | Чистый стабильный upstream, источник переносимых изменений |
| `develop` | Рабочая и планируемая default branch нашего проекта |
| `main` | Только выпуски; создаётся при подготовке первого релиза |

В upstream доступны `develop`, `rebrand-breaking`, `release-11.x`; ветки `main` нет. Локальная `vendor/pineconemc` отслеживает `upstream/release-11.x`, но обновлять её следует только до проверенного стабильного тега: обычный `git pull` может захватить ещё не выпущенные изменения. При переходе upstream на следующую релизную линию настройку tracking нужно пересмотреть. Автоматическое обновление по расписанию не настроено.

После завершения текущего слияния порядок обновления следующий:

1. Проверить чистоту рабочей папки и выполнить `git fetch upstream --tags`.
2. Выбрать последний стабильный релиз по GitHub Releases, изучить патчноуты PineconeMC и исправления безопасности Prism. Рекомендуемая частота проверки — раз в неделю и отдельно при уведомлении об уязвимости.
3. Переключиться на `vendor/pineconemc` и выполнить `git merge --ff-only <проверенный-тег>`. Если fast-forward невозможен, остановиться и исследовать расхождение; не применять reset или force push.
4. Вернуться в `develop` и по поручению владельца подготовить обычное слияние `vendor/pineconemc`. Не использовать squash: общая история нужна для следующих обновлений.
5. Проверить конфликты в версии и удалённых нами файлах; ненужные upstream-файлы и workflow восстанавливать не требуется. Обновить субмодуль, локально проверить Windows-сборку, запуск и важные сценарии.
6. Обновить запись о базе в этом документе. Переносить в `CHANGELOG.md` только изменения поведения нашего лаунчера; собственную версию менять независимо от номера upstream.

Допускается перенос отдельных важных исправлений, если полный merge пока нежелателен. Для таких исправлений следует сохранять ссылку на исходный commit; cherry-pick не заменяет общую родительскую связь для последующих полных слияний.

## Целевая платформа и структура

Поддерживается только Windows 10/11 x64. Сборка и упаковка выполняются локально; базовый кандидат — пресет `windows_msvc` с MSVC x64. Другие пресеты и платформенные файлы upstream могут оставаться в дереве до очистки; их наличие не означает поддержку Linux, macOS или Windows ARM64.

В `develop` удалены унаследованные GitHub Actions workflows: автоматические сборки, упаковка, публикация и служебная автоматизация не используются. На GitHub размещаются код и документация; бинарники и установщики не загружаются в Git, Releases или Actions artifacts. Результаты локальной работы храните в `build/`, `install/` и `dist/`, исключённых из Git. Новые выходные каталоги также нужно исключать явно; тестовые файлы исходников не следует скрывать глобальными правилами для всех архивов.

Сохранение структуры исходного репозитория не является требованием. В `develop` можно удалять ненужные документы, workflows и платформенные компоненты, проверяя зависимости сборки и сохраняя обязательные лицензии и уведомления. Ветка `vendor/pineconemc` остаётся чистой независимо от этих удалений.

После проверки корня удалены `.github/`, `nix/`, файлы Nix/direnv, `Containerfile`, `renovate.json`, `CODE_OF_CONDUCT.md`, `CONTRIBUTING.md`, настройки markdownlint и `.git-blame-ignore-revs`. Они относились к инфраструктуре upstream и не нужны для одиночной локальной разработки Windows-версии.

Удалён и `epl_metadata.json`: ссылок на него в локальных исходниках и настройках сборки не найдено; текущий `launcher/minecraft/update/ElyPatchTask.cpp` получает версии `by.ely.authlib` через индекс метаданных. Код авторизации и применения Ely.by-патчей сохранён. Работа этих сценариев ещё требует проверки в собранном приложении.

`.clang-format` и `.clang-tidy` сохранены: они явно используются целями форматирования и анализатором в CMake. `COPYING.md` сохранён вместе с `LICENSE`: на него ссылается `launcher/resources/documents/documents.qrc`. Настройки vcpkg сохранены для установки зависимостей MSVC. `cmake --list-presets` после очистки успешно показывает Windows-пресеты; это не проверка полной сборки.

Собственная версия, теги, патчноуты и выпуск описаны в [RELEASING.md](RELEASING.md). Полная сборка и запуск приложения ещё не проверены.

## Инструменты и зависимости

| Компонент | Что проверить | Возможный способ подготовки |
| --- | --- | --- |
| Git | Доступность и работу субмодулей | Существующая установка или Git for Windows |
| CMake | Версию относительно требований upstream | Существующая установка или локальный набор инструментов |
| C++ компилятор | Поддерживаемый upstream компилятор и архитектуру x64 | Visual Studio Build Tools с компонентами C++, если требуется MSVC |
| Windows SDK | Совместимость с выбранным компилятором | Компонент выбранного набора сборки |
| Qt6 | Требуемую версию и модули, соответствие ABI компилятора | Отдельный Qt Kit под выбранный компилятор |
| Генератор сборки | Поддержку выбранного генератора | Ninja либо генератор Visual Studio по инструкции upstream |
| Прочие библиотеки | CMake, субмодули и конфигурацию CI | Механизм, используемый upstream, без произвольной замены |
| Java | Нужна ли для сборки, вспомогательных задач или только запуска игры | Версия по требованиям upstream и выбранного Minecraft |

Это кандидаты для проверки, а не подтверждённый полный список. Не устанавливайте всё заранее. Сначала изучите официальные инструкции и исходную конфигурацию Windows CI в чистой `vendor/pineconemc`: например, `git show vendor/pineconemc:.github/workflows/build.yml`. Наш проект не запускает эти workflow. Не меняйте системный `PATH`, реестр и политики ради пробной сборки; используйте отдельную сессию и локальные пути, где это возможно.

## Проверка исходной сборки

Сначала соберите неизменённый commit upstream в отдельном каталоге сборки. Точные команды CMake добавляются в этот документ после проверки инструкций проекта: генератор, Qt Kit, параметры и имена целей пока неизвестны.

1. Записать версии Windows, Git, CMake, компилятора, SDK, Qt и генератора.
2. Проверить чистоту исходников и состояние субмодулей.
3. Выполнить конфигурацию CMake по официальной инструкции; сохранить команду и журнал.
4. Собрать требуемую конфигурацию и сохранить первый существенный сбой, если он возникнет.
5. Запустить доступные проверки upstream, если окружение позволяет.
6. Попробовать открыть приложение и проверить появление главного окна. Сам по себе этот запуск не подтверждает авторизацию, загрузку игры или все целевые возможности.

Для ошибки укажите стадию, команду, сообщение, установленную причину либо гипотезу и следующий проверяемый шаг. Не заменяйте отсутствующую зависимость изменением функциональности лаунчера.
