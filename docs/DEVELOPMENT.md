# Подготовка окружения и сборка

## База проекта

Remote `origin` указывает на `https://github.com/Duby67/OldMoneyTatarin.git`, remote `upstream` — на `https://github.com/ElyPrismLauncher/Launcher.git`.

На 14 ноября 2026 года выбран последний стабильный PineconeMC `11.1.2`, commit `ac99ad44ef98dd73dd9626c7b7b2b668dd8cbd5c`. Чистая ветка `vendor/pineconemc` содержит полное дерево этого релиза и его историю, без наших документов и изменений. В отличие от ранее импортированной `develop` upstream, стабильная база содержит исправление проверки пути при импорте CurseForge-модпаков. В [релизе Prism 11.1.1](https://github.com/PrismLauncher/PrismLauncher/releases/tag/11.1.1) оно описано как исправление безопасности.

Субмодуль `libraries/libnbtplusplus` получен на commit `3538933614059f0f44388a2b16f3db25ce42285b`. После смены базы выполняется `git submodule update --init --recursive`.

Наш `develop` ранее содержал импорт дерева upstream без родительской связи. Переход на стабильную базу завершён merge-коммитом `a4be236fb`: сохранена история нашего проекта и добавлена история `vendor/pineconemc`, дерево исходников заменено стабильным, наши документы сохранены. Незавершённого слияния сейчас нет.

Отдельная копия исходного README в нашей документации больше не требуется: оригинал доступен через `git show vendor/pineconemc:README.md`.

## Ветки и обновление upstream

| Ветка | Назначение |
| --- | --- |
| `vendor/pineconemc` | Чистый стабильный upstream, источник переносимых изменений |
| `develop` | Рабочая и планируемая default branch нашего проекта |
| `main` | Только выпуски; создаётся при подготовке первого релиза |

В upstream доступны `develop`, `rebrand-breaking`, `release-11.x`; ветки `main` нет. Локальная `vendor/pineconemc` отслеживает `upstream/release-11.x`, но обновлять её следует только до проверенного стабильного тега: обычный `git pull` может захватить ещё не выпущенные изменения. При переходе upstream на следующую релизную линию настройку tracking нужно пересмотреть. Автоматическое обновление по расписанию не настроено.

Порядок обновления следующий:

1. Проверить чистоту рабочей папки и выполнить `git fetch upstream --tags`.
2. Выбрать последний стабильный релиз по GitHub Releases, изучить патчноуты PineconeMC и исправления безопасности Prism. Рекомендуемая частота проверки — раз в неделю и отдельно при уведомлении об уязвимости.
3. Переключиться на `vendor/pineconemc` и выполнить `git merge --ff-only <проверенный-тег>`. Если fast-forward невозможен, остановиться и исследовать расхождение; не применять reset или force push.
4. Вернуться в `develop` и по поручению владельца подготовить обычное слияние `vendor/pineconemc`. Не использовать squash: общая история нужна для следующих обновлений.
5. Проверить конфликты в версии и удалённых нами файлах; ненужные upstream-файлы и workflow восстанавливать не требуется. Обновить субмодуль, локально проверить Windows-сборку, запуск и важные сценарии.
6. Обновить запись о базе в этом документе. Переносить в `CHANGELOG.md` только изменения поведения нашего лаунчера; собственную версию менять независимо от номера upstream.

Допускается перенос отдельных важных исправлений, если полный merge пока нежелателен. Для таких исправлений следует сохранять ссылку на исходный commit; cherry-pick не заменяет общую родительскую связь для последующих полных слияний.

## Целевая платформа и структура

Поддерживается только Windows 10/11 x64. Единственный пресет — `windows_msvc` с MSVC x64; CMake отклоняет другие ОС и 32-битную сборку. Удалены сборочные ветки и пакеты ресурсов macOS/Linux, D-Bus/GameMode, Unix-скрипт запуска, desktop/MIME-файлы и man-страница. Общие C++ файлы могут сохранять условные платформенные фрагменты upstream; переработка функций в эту очистку не входит.

В `develop` удалены унаследованные GitHub Actions workflows: автоматические сборки, упаковка, публикация и служебная автоматизация не используются. На GitHub размещаются код и документация; бинарники и установщики не загружаются в Git, Releases или Actions artifacts. Результаты локальной работы храните в `dist/`, локальные инструменты — в `.cache/`, исключённых из Git. Новые выходные каталоги также нужно исключать явно; тестовые файлы исходников не следует скрывать глобальными правилами для всех архивов.

Сохранение структуры исходного репозитория не является требованием. В `develop` можно удалять ненужные документы, workflows и платформенные компоненты, проверяя зависимости сборки и сохраняя обязательные лицензии и уведомления. Ветка `vendor/pineconemc` остаётся чистой независимо от этих удалений.

После проверки корня удалены `.github/`, `nix/`, файлы Nix/direnv, `Containerfile`, `renovate.json`, `CODE_OF_CONDUCT.md`, `CONTRIBUTING.md`, настройки markdownlint и `.git-blame-ignore-revs`. Они относились к инфраструктуре upstream и не нужны для одиночной локальной разработки Windows-версии.

Удалён и `epl_metadata.json`: ссылок на него в локальных исходниках и настройках сборки не найдено; текущий `launcher/minecraft/update/ElyPatchTask.cpp` получает версии `by.ely.authlib` через индекс метаданных. Код авторизации и применения Ely.by-патчей сохранён. Работа этих сценариев ещё требует проверки в собранном приложении.

`.clang-format` и `.clang-tidy` сохранены: они явно используются целями форматирования и анализатором в CMake. `COPYING.md` сохранён вместе с `LICENSE`: на него ссылается `launcher/resources/documents/documents.qrc`. Настройки vcpkg сохранены для установки зависимостей MSVC. `cmake --list-presets` после очистки показывает только `windows_msvc`.

Собственная версия, теги, патчноуты и выпуск описаны в [RELEASING.md](RELEASING.md). Локальная Release-сборка и установка проверены; запуск приложения и игры проверяются отдельно.

## Локальное окружение Windows x64

Для текущей подготовки используются Visual Studio Build Tools 2026 с MSVC x64, CMake 4.3.1, Ninja 1.12.1, Qt 6.10.2 (MSVC 2022 64-bit) и JDK 17. Qt нужны компоненты NetworkAuth и Image Formats; SVG входит в выбранный комплект. Зависимости C++ перечислены в `vcpkg.json` и фиксируются baseline из `vcpkg-configuration.json`.

Qt, JDK и vcpkg можно хранить локально в исключённом из Git `.cache/deps/`. Существующие системные инструменты не переустанавливаются. Подготовленная копия vcpkg соответствует baseline `2d6a6cf3ac9a7cc93942c3d289a2f9c661a6f4a7`; после выбора этой ревизии необходимо запускать её `bootstrap-vcpkg.bat`, чтобы версия исполняемого файла соответствовала формату конфигурации инструментов.

JDK 22 не подходит для старого уровня Java-исходников проекта. Используйте JDK 17; системную Java менять не требуется.

## Сборка и установка

Из корня проекта в PowerShell:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/build.ps1 -Jobs 6 -Install
```

`ExecutionPolicy Bypass` относится только к запущенному процессу; системная политика не меняется. Скрипт подключает окружение MSVC x64 через установленный Visual Studio Build Tools, находит Ninja и передаёт Qt и Java в CMake. При отсутствии инструмента он завершается с сообщением об ошибке. Первый запуск CMake загружает и собирает зависимости vcpkg; требуется интернет.

По умолчанию используются `.cache/deps/Qt/6.10.2/msvc2022_64`, `.cache/deps/vcpkg` и единственный JDK в `.cache/deps/java/`. Другие установки задаются явно:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/build.ps1 -QtRoot C:/Qt/6.10.2/msvc2022_64 -VcpkgRoot C:/Tools/vcpkg -JavaHome C:/Tools/jdk-17 -Install
```

Дополнительные параметры: `-Configuration Debug` или `Release` (по умолчанию), `-Jobs` для параллелизма, `-ConfigureOnly` для одной конфигурации CMake. `-Install` копирует готовое приложение и библиотеки в локальный каталог; без него выполняется только сборка. LTO для этой проверочной сборки отключён.

| Каталог | Содержимое |
| --- | --- |
| `dist/build/windows_msvc/` | CMake, промежуточные файлы и результаты компиляции |
| `dist/app/windows_msvc/` | Локальная установка с зависимостями после `-Install` |
| `dist/vcpkg_installed/` | Собранные зависимости C++ |
| `dist/logs/` | Журналы проверочных запусков |
| `.cache/deps/` | Локальные инструменты и их загрузки |

Эти каталоги исключены из Git. Версия приложения берётся из `VERSION`, порядок выпуска описан в [RELEASING.md](RELEASING.md). Упаковка отдельного установщика и публикация бинарников в эту процедуру не входят.
