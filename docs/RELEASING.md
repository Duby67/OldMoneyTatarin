# Выпуск

## Версия

Единственный источник версии продукта — `VERSION`: одна строка `vX.Y.Z` без ведущих нулей и суффиксов. CMake получает из неё версию приложения `X.Y.Z` и Windows-ресурсов `X.Y.Z.0`. Версия OldMoneyTatarin не зависит от номера PineconeMC.

## Патчноуты

В `CHANGELOG.md` записываются только изменения поведения лаунчера. Перед PR в
`main` заранее повысьте `VERSION` и замените `Unreleased` датированным разделом
этой версии со ссылкой на будущий тег. Тег на этом этапе создавать не нужно:

```markdown
## [v0.3.0](https://github.com/Duby67/OldMoneyTatarin/releases/tag/v0.3.0) — YYYY-MM-DD

### Исправлено

- Описание исправления для пользователя.
```

Укажите реальную календарную дату. Заголовок версии должен быть уникальным, раздел — содержать хотя бы один пункт. Из него извлекается текст до следующего заголовка версии.

Подготовка патчноутов в PowerShell:

```powershell
$releaseTag = (Get-Content -Raw VERSION).Trim()
python scripts/prepare_release.py --tag $releaseTag --notes-file release-notes.md
```

Скрипт проверяет совпадение тега с `VERSION`, ссылку на тег, дату и патчноуты.
Текущая версия должна быть первым разделом выпуска; неперенесённые записи
`Unreleased` не допускаются. Локальный `release-notes.md` исключён из Git.

## Порядок выпуска

1. В `develop` обновить `VERSION` и подготовить раздел патчноутов со ссылкой на будущий тег.
2. Локально [собрать приложение](DEVELOPMENT.md), проверить Ely.by, установку и запуск игры, обновление существующего профиля.
3. Проверить состав пакета, условия распространения и подпись перед передачей пользователям.
4. По отдельному поручению опубликовать `develop` и открыть PR `develop` → `main`. Проверка `release-validation` требует увеличения версии относительно `main`.
5. После проверки слить PR в `main`. Workflow создаст тег из `VERSION` на коммите слияния и стабильный Release с описанием из соответствующего раздела `CHANGELOG.md`.
6. По отдельному поручению вручную прикрепить проверенный локальный установщик к этому Release. Выпуск готов к распространению после загрузки установщика.

## Автоматизация GitHub

`.github/workflows/release.yml` выполняет только проверку метаданных и публикацию
текстового релиза. Приложение не собирается; бинарники и Actions artifacts не
загружаются. Публикация срабатывает после merge внутреннего PR `develop` → `main`;
открытый или просто закрытый без merge PR ничего не публикует. Кнопка Run workflow
проверяет метаданные на `develop`, не создаёт тегов и релизов.

У задания проверки права `contents: read`, у публикации — `contents: write`.
Используется встроенный `GITHUB_TOKEN`, отдельный секрет не требуется. Ветка
`main` требует PR и успешный `release-validation`; прямой push и force-push
запрещены. Рабочая ветка по умолчанию остаётся `develop`.

Публикация идёт через `scripts/publish_release.py`: checkout должен совпасть с
`merge_commit_sha` события. Теги не перезаписываются; существующий Release при
повторном запуске принимается только с тем же коммитом и патчноутом. Выпуск не
может понизить Latest. Если тег создался, а запрос создания Release завершился
ошибкой, повторите завершившийся workflow через Re-run jobs.

Проверки скриптов: `python -m unittest discover -s tests/release -p '*_test.py'`.
`prepare_release.py` сам ничего не публикует. GitHub Release запускает обнаружение
новой версии лаунчером; скачивание и автоматическая установка приложения пока
не реализованы. Готовый установщик добавляется вручную в Assets соответствующего
Release; workflow его не загружает.

## Локальный установщик Windows

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/build.ps1 -Jobs 6 -Installer
```

CMake ищет локальный Inno Setup 6 (`ISCC.exe`) в PATH, реестре и стандартных папках.
Другой путь можно задать через `-DOldMoneyTatarin_ISCC_EXECUTABLE=<путь-к-ISCC.exe>`
при конфигурации CMake. Обычная сборка не требует Inno Setup.
После конфигурации доступна также команда:

```powershell
cmake --build dist/build/windows_msvc --config Release --target installer
```

Цель `installer` готовит чистую установку приложения в каталоге сборки, добавляет
распространяемые библиотеки MSVC и уведомления лаунчера, затем компилирует
`installer/windows.iss.in`. Результат — `dist/installer/OldMoneyTatarin-X.Y.Z-Setup-x64.exe`;
версия берётся из `VERSION`. Упаковка разрешена только для Release.

Мастер на русском: выбор папки → установка → завершение. Папка по умолчанию —
`%LOCALAPPDATA%\Programs\OldMoneyTatarin`, при повторной установке сохраняется
ранее выбранная папка. Установка выполняется для текущего пользователя без
запроса администратора и создаёт ярлык в меню «Пуск». Выбора компонентов,
дополнительных задач и языка нет. На последней странице есть флажок
«Открыть лаунчер»; при тихой установке приложение не запускается.
Лицензии включены в файлы пакета без отдельного шага принятия.
Удаление через стандартный деинсталлятор не очищает пользовательские данные лаунчера.
Подпись выполняется отдельными целями, описанными ниже.

Проверены компиляция Inno Setup, тихая установка в отдельную тестовую папку,
наличие библиотек runtime и лицензий, удаление приложения и сохранность
постороннего файла после удаления. Последовательность экранов задана в сценарии;
визуальная проверка мастера пока не выполнялась.

## Локальная подпись Windows

Издатель установщика — `TATARIN`, компания в Windows-ресурсах — `TATARIN Co.`.
Уведомления и лицензии upstream сохраняются в пакете.

Первичная настройка локального самоподписанного сертификата:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/create-signing-certificate.ps1
```

Сертификат `CN=TATARIN, O=TATARIN Co.` с назначением Code Signing создаётся
в `Cert:\CurrentUser\My` на три года. Закрытый ключ неэкспортируемый, хранится
в Windows у текущего пользователя. Скрипт не добавляет сертификат в доверенные
хранилища. В исключённом из Git каталоге `secrets/codesigning/` остаются только
публичный `TATARIN.cer` и `thumbprint.txt`. Повторный запуск сохраняет существующий
сертификат; потеря Windows-профиля означает потерю доступа к этому ключу.

После обычной конфигурации CMake доступны отдельные цели:

```powershell
cmake --build dist/build/windows_msvc --config Release --target sign-launcher
cmake --build dist/build/windows_msvc --config Release --target installer-signed
```

`sign-launcher` собирает и подписывает exe лаунчера и filelink в каталоге сборки.
`installer-signed` подписывает их свежие копии в staging, упаковывает приложение,
затем подписывает готовый установщик. Нужен SignTool из локального Windows SDK;
алгоритм подписи — SHA-256. Обычные цели сборки и `installer` не подписывают файлы.
Сгенерированный Inno Setup деинсталлятор этой схемой не подписывается.

Путь к файлу отпечатка можно изменить параметром CMake
`OldMoneyTatarin_SIGNING_THUMBPRINT_FILE`; сертификат должен находиться
в личном хранилище текущего пользователя и иметь закрытый ключ.
Необязательный `OldMoneyTatarin_SIGNING_TIMESTAMP_URL` задаёт HTTPS-сервер
RFC 3161; по умолчанию временная метка не запрашивается.

Самоподписанный сертификат не обеспечивает доверие Windows и SmartScreen
на чужих компьютерах. Для публичной доверенной подписи нужен сертификат
от доверенного центра сертификации и подходящий способ доступа к его ключу.
См. [документацию Microsoft](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.core/about/about_signing).
Для 0.4.0 проверены полный цикл `installer-signed`, подписи лаунчера, filelink
и установщика с издателем TATARIN, версия Windows-ресурсов и компания TATARIN Co.
Проверен запуск полного приложения в отдельном профиле и оба результата проверки
обновлений. Последняя страница мастера и интерактивная установка поверх
пользовательской 0.3.0 вручную не проверялись.

## Ручная загрузка установщика в Release

Для каждого выпуска локально соберите и проверьте установщик из коммита,
на который указывает тег выпуска. Версия файла должна совпадать с тегом:
для `vX.Y.Z` загрузите `dist/installer/OldMoneyTatarin-X.Y.Z-Setup-x64.exe`.

После создания Release откройте на GitHub **Releases → нужная версия → Edit**,
прикрепите `.exe` в поле загрузки файлов и сохраните через **Update release**.
Убедитесь, что установщик появился в **Assets** и доступен для скачивания.
Не добавляйте его в Git и не используйте Actions artifacts для распространения.

GitHub поддерживает прикрепление бинарных файлов к релизам;
[инструкция GitHub](https://docs.github.com/en/repositories/releasing-projects-on-github/managing-releases-in-a-repository).
Этот порядок требует отключённой неизменяемости релизов (immutable releases):
при включённой неизменяемости добавить файл после публикации нельзя. Для такого
режима потребуется отдельно изменить workflow на создание draft с последующей
ручной загрузкой и публикацией. Текущая настройка неизменяемости репозитория
не проверена.

## Проверка обновлений лаунчера

Начиная с 0.2.0 лаунчер проверяет стабильные выпуски при каждом запуске, если
автоматическая проверка включена. Дополнительный интервал в настройках задаётся
в часах; 0 означает проверку при запуске. Ручная команда — «Проверить обновления».
Результат показывается в строке состояния и сохраняется в настройках лаунчера.
При обнаружении более новой версии появляется окно с патчноутом и кнопкой
открытия страницы выпуска. Лаунчер не скачивает и не запускает установщик автоматически.

По умолчанию используется GitHub API `releases/latest` для репозитория из
`Launcher_UPDATER_GITHUB_REPO`. Нужен опубликованный публичный стабильный релиз
с тегом `vX.Y.Z`: draft и prerelease не принимаются. Формат API описан в
[документации GitHub](https://docs.github.com/en/rest/releases/releases#get-the-latest-release).
Версии сравниваются численно; более старый выпуск не предлагается как обновление.
Ошибка сети, отсутствие релиза, повреждённый ответ и ограничение запросов не
считаются подтверждением актуальности установленной версии.

Для публичного канала прикрепите локальный установщик к GitHub Release по инструкции
выше. Тег и Release создаются workflow после согласованного merge в `main`;
push, merge и загрузка установщика выполняются отдельным поручением. Проверка
обновлений ориентируется на версию Release и может обнаружить её ещё до ручной
загрузки установщика.

В разделе обновлений настроек можно указать «Источник обновлений» — URL JSON
с полями GitHub Release `tag_name`, `draft`, `prerelease`, `html_url`, `body`.
Пустой адрес включает GitHub по умолчанию. Разрешён HTTPS, для разработки также
HTTP на `127.0.0.1`. Редиректы, credentials и параметры query в адресах отклоняются.
Подпись пакетов и автоматическая замена файлов приложения пока не реализованы.

## Локальная проверка 0.2.0 → 0.3.0

После сборки установщика 0.2.0:

```powershell
python scripts/launcher_updates.py publish --installer dist/installer/OldMoneyTatarin-0.2.0-Setup-x64.exe
python scripts/launcher_updates.py serve
```

Установите 0.2.0, в настройках обновлений укажите
`http://127.0.0.1:18766/latest.json`, оставьте автоматическую проверку включённой.
При ручной проверке или перезапуске результатом будет отсутствие обновлений.
Локальный сервер должен работать во время проверки.

Затем, после подготовки версии 0.3.0 в `VERSION` и `CHANGELOG.md`, соберите её
установщик и выполните публикацию тем же скриптом с новым именем установщика.
Скрипт сначала копирует готовый файл и создаёт страницу выпуска, затем атомарно
обновляет `latest.json`. Установленная 0.2.0 после перезапуска должна предложить
0.3.0. Устанавливать 0.3.0 заранее для проверки не требуется.
Публикация локальная, файлы находятся в исключённом из Git `run/launcher-updates/`.
Номер уже опубликованного локального выпуска повторно использовать нельзя.

Сетевые проверки: отдельный CMake-проект `tests/updates`, затем
`python tests/updates/integration.py <путь-к-update-check.exe>` с Qt DLL в `PATH`.
Проверены числовое сравнение версий и 14 сетевых сценариев: новая/текущая/старая
версия, ошибки HTTP, draft/prerelease, повреждённый JSON, опасный адрес,
превышение размера, редирект и тайм-аут.

`tests/updates/application_smoke.py` запускает полный лаунчер через Qt offscreen
в отдельных профилях без личных аккаунтов. Ему передаются путь к exe и каталог
плагинов Qt. В 0.2.0 проверено автоматическое получение обоих результатов:
отсутствие обновлений для 0.2.0 и обнаружение тестового выпуска 0.3.0.
Внешний вид уведомления и переход в браузер вручную ещё не проверены.
