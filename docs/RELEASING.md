# Версия и выпуск OldMoneyTatarin

## Источник версии

`VERSION` содержит одну строку `vX.Y.Z`, сейчас `v0.1.0`. Это начальная версия разработки, а не опубликованный выпуск. Префикс `v` обязателен; ведущие нули, суффиксы и дополнительные компоненты не допускаются.

Модуль `cmake/OldMoneyTatarinVersion.cmake` читает этот файл и определяет `OldMoneyTatarin_VERSION_TAG`, `OldMoneyTatarin_VERSION` и числовые `OldMoneyTatarin_VERSION_MAJOR`, `MINOR`, `PATCH`. В `CMakeLists.txt` они заменяют значения `Launcher_VERSION_MAJOR`, `MINOR`, `PATCH` до вычисления производных строк версии. Следовательно, приложение, Windows-ресурсы и упаковка используют нашу версию; четыре компонента Windows имеют вид `X.Y.Z.0`.

Исходная версия PineconeMC задаётся в `CMakeLists.txt` тремя переменными `Launcher_VERSION_*`; её исходные значения сохранены перед нашим подключением и доступны в чистой `vendor/pineconemc`. Их не следует менять ради выпуска OldMoneyTatarin. База upstream фиксируется отдельно в [DEVELOPMENT.md](DEVELOPMENT.md).

## Патчноуты

`CHANGELOG.md` содержит только изменения поведения лаунчера. Работы с ветками, документацией и инструментами туда не добавляются. До выпуска изменения хранятся под `## [Не выпущено]`. Перед выпуском нужные пункты переносятся в раздел:

```markdown
## [v0.1.0] — YYYY-MM-DD

### Исправлено

- Описание исправления, заметного пользователю.
```

Вместо `YYYY-MM-DD` указывается реальная дата. Дата должна быть календарной, заголовок версии — уникальным, а раздел — содержать хотя бы один пункт. Текст патчноутов выпуска извлекается из этого раздела до следующего заголовка версии. Оно не генерируется из истории коммитов.

## Локальная подготовка выпуска

1. Установить требуемую версию в `VERSION` и подготовить соответствующий датированный раздел `CHANGELOG.md`.
2. Проверить патчноуты локально: `python scripts/prepare_release.py --tag v0.1.0`. Для другой версии использовать её тег. Параметр `--notes-file release-notes.md` сохраняет текст локально; файл исключён из Git. Текущий раздел «Не выпущено» намеренно не позволяет подготовить выпуск до заполнения датированного раздела.
3. Локально собрать и упаковать приложение под Windows x64. Использовать собственную версию из `VERSION`; результаты сборки хранить в `build/`, установки — в `install/`, готовые пакеты — в `dist/`. Эти каталоги исключены из Git. Точные команды и состав зависимостей ещё предстоит проверить при первой сборке.
4. Проверить приложение на Windows 10/11 x64, включая вход Ely.by, установку и запуск игры. Полная сборка и запуск пока не выполнены.
5. По поручению владельца оформить изменения коммитами, перенести проверенное состояние `develop` в `main`, создать и отправить тег с точным значением `VERSION`. Это фиксация версии исходного кода: тег ничего автоматически не собирает и не публикует.

Ветка `main` при этой подготовке ещё не создана: её создание и первый перенос кода выполняются при подготовке первого выпуска. Настройку `develop` как default branch владелец выполняет на GitHub.

## Содержимое GitHub

В нашем репозитории размещаются код и документация, включая `VERSION` и `CHANGELOG.md`. GitHub Actions workflows удалены из `develop`: отсутствуют автоматические сборки, выпуск черновиков, загрузка исполняемых файлов, Actions artifacts и публикация в Winget или контейнерный реестр. Чистая `vendor/pineconemc` хранит оригинальные файлы upstream для просмотра истории; при будущей интеграции не восстанавливайте их автоматизацию в `develop`.

Скрипт `scripts/prepare_release.py` только проверяет версию и извлекает патчноуты. Он не создаёт Git-теги, не запускает сборку и не обращается к GitHub. Совпадение тега и `VERSION`, а также выпуск из `main` теперь проверяются вручную при локальной подготовке. Отдельный способ распространения бинарников и канал обновления лаунчера ещё не определены.

Внутренние имена исполняемых файлов, существующая упаковка и оформление upstream пока сохранены; собственный установщик не разрабатывался. Подпись локальных пакетов требует отдельной подготовки.

Ранее адрес `Launcher_UPDATER_GITHUB_REPO` был переведён на наш репозиторий. Поскольку бинарники там не публикуются, это не рабочий канал обновления. Его настройка для будущего внешнего распространения и проверка совместимости тегов `vX.Y.Z` выполняются отдельным заданием; текущая подготовка не подтверждает работоспособность автообновления.
